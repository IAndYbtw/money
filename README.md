# FinBot — Telegram-бот для анализа трат

## Структура проекта

```
finbot/
├── bot.py           # все команды-хендлеры (aiogram)
├── db.py            # SQLite: транзакции, доходы, цели
├── categorizer.py   # парсинг текста → сумма + автокатегория
├── analytics.py      # сводки, детект подписок, поиск аномалий
├── ai.py             # интеграция с Claude API: промпты и вызовы
├── config.py          # чтение .env
├── requirements.txt
└── .env.example
```

## Запуск

```bash
pip install -r requirements.txt
cp .env.example .env
# заполнить BOT_TOKEN и DEEPSEEK_API_KEY в .env
python bot.py
```

## Как устроена ИИ-часть

Используется **DeepSeek API** (`deepseek-chat` — модель V3, либо `deepseek-reasoner` —
модель с рассуждениями R1). DeepSeek API полностью совместим с OpenAI SDK, поэтому
в `ai.py` используется обычный `openai.OpenAI`, только с другим `base_url`:

```python
client = OpenAI(api_key=DEEPSEEK_API_KEY, base_url="https://api.deepseek.com")
```

В отличие от Anthropic API, где системный промпт передаётся отдельным параметром
`system=...`, в OpenAI-совместимом формате он идёт первым сообщением в списке
`messages` с `role: "system"` — это учтено в `ai.py`.

Если хочешь более сильные рассуждения для сложных вопросов в `/ask` (например,
многошаговый анализ причин роста трат) — попробуй `DEEPSEEK_MODEL=deepseek-reasoner`
в `.env`. Она медленнее и дороже, но лучше объясняет "почему", а не только "что".

### Почему не отдавать в ИИ сырые данные

В `analytics.build_ai_summary()` формируется **агрегированный JSON** — суммы по
категориям, изменения месяц к месяцу, найденные подписки. Никаких номеров карт,
получателей платежей с реквизитами и т.п. Это и дешевле (меньше токенов), и
безопаснее — модель не должна видеть сырые банковские данные.

Пример того, что реально летит в API:

```json
{
  "week": {"total": 12400, "by_category": [{"category": "Такси", "total": 4100, "count": 6}]},
  "month": {"total": 48000, "by_category": [...]},
  "month_over_month": [{"category": "Такси", "current": 7800, "previous": 3200, "change_pct": 144}],
  "subscriptions": [{"name": "яндекс плюс", "amount": 399, "period_days": 30, "days_since_last": 40}],
  "currency": "₽"
}
```

### Системный промпт (`ai.SYSTEM_PROMPT`)

Задаёт роль и жёсткие рамки — это главный рычаг качества:
- отвечать только на основе переданных данных (запрет на выдумывание цифр);
- формат ответа (пункты с эмодзи, коротко);
- запрет на общие советы без опоры на конкретные цифры пользователя;
- что делать при недостатке данных — честно сказать, а не придумывать.

Чем более узко и конкретно сформулирован системный промпт, тем меньше модель
уходит в "воду". Если увидишь, что ответы становятся общими — в первую очередь
дорабатывай именно эту часть, а не пользовательский промпт.

### Два сценария использования

1. **`generate_insights(summary)`** — команда `/insights`. Один вызов,
   без истории диалога, promt строится сразу с полной сводкой.

2. **`answer_question(summary, question, history)`** — команда `/ask`.
   Поддерживает историю диалога (последние 10 сообщений хранятся в памяти
   процесса в `bot.py` — для продакшена вынести в Redis или БД, чтобы не
   терять контекст при перезапуске бота).

### Как вывести ответ обратно в бота

Вызов Claude возвращает объект с `response.content` — списком блоков
(`text`, возможно `tool_use` и т.д.). Функция `_extract_text()` в `ai.py`
склеивает текстовые блоки в одну строку, которую хендлер в `bot.py`
просто отправляет через `message.answer(text)`. Никакой дополнительной
обработки не нужно, если не просить модель отвечать в JSON.

### Если нужен структурированный ответ (например, для Mini App)

Если в будущем захочешь не текст, а JSON (например, чтобы отрисовать
рекомендации как карточки в Mini App), в системный промпт добавляется
жёсткое требование:

```
Отвечай ТОЛЬКО валидным JSON вида:
{"insights": [{"title": "...", "detail": "...", "saving_estimate": 1234}]}
Никакого текста до или после JSON.
```

И на стороне кода — `json.loads(text)` с обработкой `try/except`, потому что
модель иногда всё равно оборачивает ответ в ```json ... ``` — это нужно
чистить перед парсингом (`text.strip("`").replace("json\n", "")` или
регуляркой).

### Стоимость и лимиты

- `/insights` и `/ask` — единственные команды, которые дергают внешний API,
  остальное (парсинг, категоризация, сводки, детект подписок) — чистый код,
  без ИИ и без затрат.
- Есть смысл кэшировать `/insights` на день — вряд ли пользователю нужен
  новый анализ каждые 5 минут, а токены экономятся заметно.

## Что дальше (идеи для развития)

- **Mini App**: `/app` пока заглушка. Дальше — `WebAppInfo(url=...)`,
  фронт с графиками (Chart.js/Recharts), авторизация через `initData`.
- **Загрузка банковских выписок**: PDF/CSV → парсинг → автоматическое
  заполнение транзакций вместо ручного ввода.
- **Напоминания**: `aiogram` job scheduler (`apscheduler`) — например,
  еженедельная сводка без команды, как в примерах выше.
- **Многопользовательские категории**: сейчас категории общие для всех,
  можно дать юзеру возможность добавлять свои ключевые слова.
